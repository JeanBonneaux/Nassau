## Q1. Protocole local (transport, port, TLS, découverte, topics) et obtention des identifiants (BLID et mot de passe)

### Takeaway
Les Roomba Wi-Fi « classiques » (séries 600, 800, 900, e, i, s, j) hébergent un **broker MQTT sur TLS, port 8883**. Le nom d'utilisateur et le client-id sont le **BLID**, le mot de passe est une chaîne propre au robot (`:1:<horodatage>:<aléa>`). La découverte se fait par **broadcast UDP `irobotmcs` sur le port 5678**. Les commandes sont publiées en JSON sur le topic `cmd`, les réglages sur `delta`, et le robot publie son état sur `$aws/things/<BLID>/shadow/update` et `wifistat`. Un 694 (firmware 3.5.18+we+8) a été vu en novembre 2026 en train d'accepter la connexion et de diffuser son état, avec une particularité : il n'envoie jamais de SUBACK. Deux façons d'obtenir le mot de passe : (a) en local, robot sur sa base et réveillé, après un appui sur HOME (ou HOME+SPOT sur les 600) jusqu'aux bips, puis requête TLS sur 8883 dans les 30 s ; (b) depuis le compte cloud iRobot (dorita980 `get-roomba-password-cloud`, Roomba980-Python `password.py`). Pour le 694, la seule réussite documentée passe par la méthode cloud ; la récupération locale a échoué dans les deux rapports trouvés (2025 et 2026).

### Cited Findings

**Transport, port, TLS**
- dorita980 : « targets the local MQTT/TLS protocol used by older Wi‑Fi Roombas » ; familles connues : « Roomba 600, 800, and 900 series (e.g. 675, 690, 960, 980) » [autre modèle: série 600 générique, 675, 690] — [README dorita980](https://github.com/koalazak/dorita980) (README consulté le 2026-11-08 ; dorita980 4.0.0 publié sur npm le 2026-02-27 : [npm](https://www.npmjs.com/package/dorita980)).
- Test réseau recommandé : « `nc -zv <robot_ip> 8883` » [non confirmé] — [README dorita980](https://github.com/koalazak/dorita980).
- Port 8883 et TLS permissif dans roombapy (bibliothèque de Home Assistant) : `DEFAULT_PORT = 8883`. Le commentaire de `tls.py` dit : « these robots present self-signed certificates, negotiate small Diffie-Hellman parameters, and older firmware needs legacy renegotiation ». Le contexte applique `check_hostname = False`, `CERT_NONE`, `set_ciphers("DEFAULT:!DH")` et `OP_LEGACY_SERVER_CONNECT` (« without this the handshake fails outright against OpenSSL 3 ») [non confirmé] — [roombapy tls.py](https://github.com/pschmitt/roombapy/blob/main/roombapy/tls.py), [roombapy getpassword.py](https://github.com/pschmitt/roombapy/blob/main/roombapy/getpassword.py) (branche main, consultée le 2026-11-08).
- Suite de chiffrement par défaut de dorita980 : « Default is `AES128-SHA256` », modifiable par `ROBOT_CIPHERS` (exemple `AES128-SHA`). Variable `ROBOT_TLS_LEGACY=0` pour désactiver la renégociation héritée, que dorita980 active désormais par défaut [non confirmé] — [README dorita980](https://github.com/koalazak/dorita980).
- **Contradiction ou variante selon les modèles** : le binding openHAB indique que « Some Roomba models use an outdated TLS configuration and require the legacy cipher `TLS_RSA_WITH_AES_256_CBC_SHA` », suite désactivée par défaut à partir d'OpenJDK 21.0.10. Le modèle concerné n'est pas nommé [non confirmé] — [README binding openHAB irobot](https://github.com/openhab/openhab-addons/blob/main/bundles/org.openhab.binding.irobot/README.md) (consulté le 2026-11-08).
- Sur une série 600 non précisée : « Some roombas (such as my 600 series) do not support "RFC 5746 secure renegotiation" » et « Newer versions of Python use OpenSSL 3, which enforces this standard by default » [autre modèle: série 600 générique] — [roombapy issue #175](https://github.com/pschmitt/roombapy/issues/175) (2023-03-06).

**Session MQTT, topics, messages**
- **Capture sur un 694** (roombapy 2.0.2, robot « Roomba 694, SKU r694020, sw 3.5.18+we+8, discovery ver 3, proto mqtt »). Le client envoie un CONNECT avec client_id = BLID, clean session, keepalive 60. Le robot répond CONNACK (0,0) en ~48 ms. Le client s'abonne à `#` en QoS 0, puis reçoit des PUBLISH sur `wifistat` (336 octets) et `$aws/things/<BLID>/shadow/update` (1333 octets). **Aucun SUBACK n'arrive** [694 confirmé] — [roombapy issue #624](https://github.com/pschmitt/roombapy/issues/624) (2026-11-07 ; résumé obtenu via WebFetch, citations courtes).
- Identifiants MQTT dans le code : `identifier=self.blid`, `username=self.blid`, `password=self.password`, abonnement par défaut `topic: str = "#"` [non confirmé] — [roombapy roomba.py](https://github.com/pschmitt/roombapy/blob/main/roombapy/roomba.py).
- Format des commandes : `{"command": ..., "time": <epoch>, "initiator": "localApp"}` publié sur `cmd`. Les préférences partent sur `delta` sous la forme `{'state': newState}`. Citation : « Known topics are `cmd` and `delta` » [non confirmé] — [README dorita980](https://github.com/koalazak/dorita980) ; [roombapy roomba.py](https://github.com/pschmitt/roombapy/blob/main/roombapy/roomba.py) (`await self._publish("cmd", payload)`, `self._publish("delta", payload)`).
- Commandes listées par Roomba980-Python : « "start" "stop" "pause" "resume" "dock" "evac" (only with clean base) "reset" "locate" ». Réglages : carpetBoost, vacHigh, openOnly, noAutoPasses, twoPass, binPause [non confirmé] — [README Roomba980-Python](https://github.com/NickWaterton/Roomba980-Python). Home Assistant envoie `find` pour la fonction « locate » — [HA vacuum.py](https://github.com/home-assistant/core/blob/dev/homeassistant/components/roomba/vacuum.py).
- **État d'une série 600 (690, firmware « 3.2.40+69 », SKU « R690020 »)**, d'après la capture de 2019 dans dorita980 #71. Topic `wifistat` : netinfo, wifistat, wlcfg, signal (rssi, snr). Topic `shadow/update` : batPct, bin{present, full}, cleanMissionStatus{cycle, phase, expireM, rechrgM, error, notReady, mssnM, sqft, initiator, nMssn}, dock{known}, bbrun, bbmssn, cleanSchedule, cap `{ "ota": 1, "eco": 1, "svcConf": 1 }`, softwareVer, etc. **Ni `pose` ni `bbchg3`** [autre modèle: 690] — [dorita980 issue #71](https://github.com/koalazak/dorita980/issues/71) (commentaire du 2019-01-07, résumé WebFetch).
- Phases connues (charge, new, run, resume, hmMidMsn, recharge, stuck, dock, dockend, cancelled, stop, pause, hmPostMsn…) et table des codes d'erreur (1 « Left wheel off floor », 9 « Bumper stuck », 14 « Bin missing »…) [non confirmé] — [README openHAB](https://github.com/openhab/openhab-addons/blob/main/bundles/org.openhab.binding.irobot/README.md) ; table d'erreurs « iRobot_6.3.1-release.apk / res/values-en-rGB/strings.xml » — [roombapy const.py](https://github.com/pschmitt/roombapy/blob/main/roombapy/const.py).

- Home Assistant découvre aussi les robots par DHCP (noms d'hôte `roomba-*` / `irobot-*`, préfixes MAC 501479, 80A589, DCF505, 204EF6) et par zeroconf `_amzn-alexa._tcp.local.`. **Récupération locale du mot de passe (mécanisme)**
- Ouverture d'une connexion TLS vers 8883 et envoi de l'octet-magique `f005efcc3b2900`. La réponse est préfixée par sa longueur et le mot de passe correspond aux octets `data[7:]`. Si le robot répond `f005efcc3b2903`, le code note : « This model serves its password from the cloud only. » Docstring : « The robot must be on its dock and powered on. Press and hold HOME until a series of tones plays; release, and the Wi-Fi LED flashes. » [non confirmé] — [roombapy getpassword.py](https://github.com/pschmitt/roombapy/blob/main/roombapy/getpassword.py).
- Format du mot de passe : « Password=> :1:1486937829:gktkDoYpWaDxCfGh <= Yes, all this string. » (exemple de la documentation) [non confirmé] — [README dorita980](https://github.com/koalazak/dorita980). Même format chez un 692 en 2025 (capture d'écran de la sortie dorita980 : « sku: R692020 SoftwareVer: 3.5.18+we+8 », mot de passe au format `:1:<nombre>:<chaîne>`, partiellement masqué par l'auteur) [autre modèle: 692] — [forum HA, 2025-01-21](https://community.home-assistant.io/t/trying-to-pair-my-irobot-692-w-ha-via-irobot-roomba-device-integration/833784).

### Inferences
- Le 694 relève de la génération « Classic / v3 » (firmware 3.5.x, découverte `ver 3`, MQTT local sur 8883). Il n'appartient pas à la génération x05 / V4 « Prime », qui n'a pas d'écoute locale. Attention : la gamme récente « Roomba **Plus 600** Series » est un autre produit (voir Q5).
- La capture de dorita980 #71 montre un 690 sans `cap.carpetBoost` ni `cap.pose`. Si le 694 se comporte pareil, ce qui est plausible mais non vérifié, Home Assistant lui attribue la classe de base, sans vitesse d'aspiration ni position.
- Pour le 694, la méthode la plus robuste semble être de récupérer les identifiants depuis le cloud tant qu'il fonctionne, puis de les conserver. La récupération locale a échoué dans les deux rapports 694 trouvés.

### Gaps
- Aucune source ne décrit la combinaison de boutons propre au **694** pour le mode mot de passe (HOME seul ou HOME+SPOT, durée exacte). Les sources sur les 690, 692 et 675 suggèrent HOME+SPOT environ 2 s, robot sur sa base.
- Pas de capture TLS (version, suite négociée) pour un 694. Pas de dump d'état complet d'un 694 (seulement d'un 690 en 2019).
- Signification du suffixe « +we » et du numéro 3.5.18 par rapport à la 3.5.62 officielle : inconnue.

## Q2. Bibliothèques et intégrations : prise en charge explicite du 694 (et des 690, 692, 675), ce qui marche, ce qui ne marche pas

### Takeaway
**Aucune bibliothèque ni intégration ne liste le 694 comme testé et pris en charge.** Le 690 et le 675 figurent dans les listes de dorita980 et d'ioBroker, et Home Assistant dit « should also work fine with … the 690 ». Les rapports d'usage sur 694 sont mitigés : échec Homebridge en 2022, réussite Home Assistant en mars 2025. **Situation actuelle (novembre 2026)** : Home Assistant 2026.11.0, qui embarque roombapy 2.0.2, **ne se connecte plus à un 694 en firmware 3.5.18**. Le robot n'envoie jamais de SUBACK ; c'est une régression par rapport à roombapy 1.9.1 (HA 2026.10.x). Sur une série 600, on peut faire : start/stop/pause/resume/dock/find, lire batterie, phase, bac, erreur, statistiques de missions, RSSI, horaires. On ne peut pas : position, carte, nettoyage par pièce (absence de `pose` et de carte persistante). Aucune commande documentée ne permet de piloter les roues ni de lire les capteurs bruts en Wi-Fi.

### Cited Findings
**dorita980 / rest980 (Node.js)**
- Titre : « Unofficial iRobot Roomba (Combo 10 Max, j7, i7/i7+, 980, 960, e5, 690, 675, etc) node.js library ». Le 694 n'est pas nommé [autre modèle: 690, 675] — [README dorita980](https://github.com/koalazak/dorita980).
- Sur les séries 600, dorita980 attendait le champ `pose` et restait bloqué : « your robot (600 series) is not reporting that postion, then dorita980 wait forever ». Correctif publié dans 3.1.0 (2019-01-08). Commandes testées sur un 690 en firmware 3.2 : « `start`, `pause`, `resume`, and `end` » [autre modèle: 690] — [dorita980 #71](https://github.com/koalazak/dorita980/issues/71).
- Pour les modèles sans navigation, la doc recommande `getBasicMission()` au lieu de `getMission()`. Elle note aussi : « some new firmwares are not reporting robot position ('pose' property) to local env » [non confirmé] — [README dorita980](https://github.com/koalazak/dorita980).
- rest980 expose dorita980 en API HTTP REST (port 3000 par défaut) : « Use `2` for any firmware >=2 (yes, use 2 if you have firmware version 3) ». L'option `keepAlive: 'no'` permet de « connect and disconnect to the robot in each request (slow but leave the connection free for the official mobile app) » [non confirmé] — [README rest980](https://github.com/koalazak/rest980).

**roombapy et intégration Home Assistant « iRobot Roomba and Braava »**

## Q3. Un ESP32 ou un ESP8266 peut-il être lui-même le client local du broker du robot ?

### Takeaway
**Oui, pour l'ESP32, au moins un projet le fait** : `solarkennedy/roomba-bridge-esphome`, composant externe ESPHome. Il se connecte au broker MQTT/TLS du robot sur 8883 avec BLID et mot de passe, s'abonne à `shadow/update` et `wifistat`, publie des commandes sur `cmd`, et expose batterie, phase, bac et RSSI. Il faut d'abord récupérer BLID et mot de passe ailleurs. Le README signale un bug d'ESPHome sur les gros JSON (correctif requis). Aucun modèle testé n'est indiqué, donc rien sur les 600 ni sur le 694. Je n'ai trouvé aucun projet Tasmota, MicroPython, Arduino ou ESP8266 qui parle au broker du robot.

### Cited Findings
- « If you flash ESPHome with this component to an ESP32 (for example), it uses the Roomba's local MQTT-based API and give you access to all its command functions. » ; « Once in place, your Roomba no longer needs to connect to the internet, nor do you need the app! » (avec la réserve « assuming you disconnect it from the internet to prevent future updates from breaking anything ») [non confirmé] — [README roomba-bridge-esphome](https://github.com/solarkennedy/roomba-bridge-esphome) (dernier push 2024-10-10).
- Contrainte mémoire et parsing : « the lastest release of ESPHome has a bug which makes it crash on the large JSON payloads that Roombas produce. This [Patch](https://github.com/esphome/esphome/pull/5786) is required. » [non confirmé] — [README roomba-bridge-esphome](https://github.com/solarkennedy/roomba-bridge-esphome).
- Détails d'implémentation : `set_broker_port(8883)`, `set_username(blid)`, `set_client_id(blid)`, `set_keep_alive(60)`, `set_skip_cert_cn_check(true)`, `set_ca_certificate(ca_cert_chain_pem)` (chaîne CA embarquée). Abonnements à `"$aws/things/" + blid + "/shadow/update"` et `"wifistat"`. Publication sur `"cmd"` des commandes start, stop, pause, resume, dock, evac, find, train. Lecture de `batPct`, `cleanMissionStatus.phase`, `bin.present/full`, `signal.rssi`. JSON parsé avec `DynamicJsonDocument doc(2048)` pour les régions [non confirmé] — [roomba_bridge.cpp](https://github.com/solarkennedy/roomba-bridge-esphome/blob/master/components/roomba_bridge/roomba_bridge.cpp).
- En 2018, une tentative avec un client léger (mosquitto) sur un « embedded device » échouait au TLS. Conseil du mainteneur : « You need to setup mosquito to ignore the error validating the TLS robot's certificate on connect » (`mosquitto_tls_insecure_set`). Aucune réussite embarquée n'a été rapportée [non confirmé] — [dorita980 #65](https://github.com/koalazak/dorita980/issues/65) (2018-03-27/28).
- Contraintes TLS susceptibles de toucher un client embarqué : renégociation héritée, certificats auto-signés, suites RSA/CBC anciennes (`AES128-SHA256` par défaut chez dorita980 ; `TLS_RSA_WITH_AES_256_CBC_SHA` « for some models » chez openHAB) [non confirmé] — [roombapy tls.py](https://github.com/pschmitt/roombapy/blob/main/roombapy/tls.py), [README dorita980](https://github.com/koalazak/dorita980), [README openHAB](https://github.com/openhab/openhab-addons/blob/main/bundles/org.openhab.binding.irobot/README.md).
- Recherches GitHub infructueuses pour un client Wi-Fi local sur ESP (2026-11-08) : `roomba esp8266 wifi local`, `roomba 8883 esp32`, `dorita980 esp32`, `roomba mqtt arduino tls blid`, `irobot roomba esp32 local`. Les autres projets ESP trouvés (`esphome roomba`, `roomba esp32 mqtt`) concernent le port série (voir Hors périmètre).

### Inferences
- Le broker du 694 n'envoie pas de SUBACK ([roombapy #624](https://github.com/pschmitt/roombapy/issues/624), [694 confirmé]). Un client MQTT embarqué qui attend l'acquittement de son abonnement, ou qui en dépend, pourrait se comporter comme roombapy 2.x et décrocher. À vérifier avec le client MQTT d'ESPHome.
- Une seule connexion locale est acceptée (Q4). Un ESP32 connecté au robot empêche donc Home Assistant, rest980 ou l'application de s'y connecter en local, et inversement. Une architecture plus simple consiste à faire de l'ESP32 un pont vers votre propre broker, ou à le laisser parler à rest980.
- ESP8266 : RAM réduite et pile TLS différente. Aucune preuve de faisabilité trouvée. Avec des JSON de plus de 1,3 ko (le message `shadow/update` du 694 fait 1333 octets selon #624) et du TLS en RSA, c'est probablement serré, mais non démontré.

### Gaps
- Aucun rapport d'utilisation de roomba-bridge-esphome sur un 600 ou un 694. Aucune mesure de RAM ou de suite TLS négociée par un ESP32 face à un Roomba.
- Je n'ai pas lu le fichier de la chaîne CA embarquée du projet, donc je ne sais pas quelle autorité signe les certificats des robots.

## Q4. Problèmes connus et pièges

### Takeaway
(1) **Une seule connexion locale à la fois** : l'application, Home Assistant, un script et un ESP32 s'excluent mutuellement. L'application bascule alors sur le cloud. (2) La récupération locale du mot de passe échoue souvent, y compris sur les 692 et 694, et le cloud sert de solution de repli. (3) Problèmes TLS avec OpenSSL 3 / Python ≥ 3.10 (renégociation héritée) et Java 21.0.10 (suites RSA). (4) Régression roombapy 2.x (SUBACK) sur 694 et 671 en novembre 2026. (5) Voyants allumés en permanence tant qu'une connexion est ouverte (signalé sur 671, 675, 676, 691 et **694**). (6) Robot injoignable sauf en nettoyage chez certains utilisateurs. (7) Les mises à jour OTA peuvent casser l'accès local ; il est conseillé de bloquer l'accès Internet du robot.

### Cited Findings
- Connexion unique : « The Roomba's MQTT server only allows a single connection. Home Assistant keeps that connection open, so the iRobot app connects to your Roomba through the cloud instead. » [non confirmé] — [doc HA](https://www.home-assistant.io/integrations/roomba/) ; « There's a maximum of 1 connection at any time in local network » — [README dorita980](https://github.com/koalazak/dorita980) ; « supports only a single local connection at a time » — [README openHAB](https://github.com/openhab/openhab-addons/blob/main/bundles/org.openhab.binding.irobot/README.md) ; message de log Jeedom : « Robot Washy found but connection is refused, make sure nothing else is connected(app?), as only one connection at a time is allowed » [autre modèle: Combo 10 Max] — [community.jeedom.com](https://community.jeedom.com/t/perte-robot/147164) (2026-02-04).
- Symptôme d'une connexion déjà occupée : « Connection Error: _ssl.c:835: The handshake operation timed out … It usually means something else is already connected to the Roomba, force close the app, and **reboot the roomba** » [non confirmé] — [README Roomba980-Python](https://github.com/NickWaterton/Roomba980-Python).
- Échecs de récupération du mot de passe sur 600 : 692 (auto KO, manuel « failed to connect », 2025-01) [autre modèle: 692] — [forum HA](https://community.home-assistant.io/t/trying-to-pair-my-irobot-692-w-ha-via-irobot-roomba-device-integration/833784) ; 694 (auto KO en 2025-03, « Socket timeout » en 2026-11) [694 confirmé] — [forum HA #89](https://community.home-assistant.io/t/get-roomba-blid-pw-the-easy-way-using-windows/75107/89), [ha_roomba_plus #230](https://github.com/johnnyh1975/ha_roomba_plus/issues/230). Message d'erreur fréquent : « Error getting password, receve 7 bytes. Contournement : `OPENSSL_CONF` avec `Options = UnsafeLegacyRenegotiation` [autre modèle: s9+, 960, i6, 986] — [HA core #82775](https://github.com/home-assistant/core/issues/82775) (2022-11 à 2023-03). - Mises à jour OTA : « I recommend blocking the internet access to your robot to avoid the OTA firmware updates. ### Inferences
- Pour un projet ESP32 + Home Assistant, n'ouvrir **qu'un seul** client vers le robot et faire relayer le reste.
- Bloquer l'accès Internet du 694 protège l'accès local contre une mise à jour. Cela suppose d'avoir déjà récupéré les identifiants, puisque la méthode cloud est la plus fiable pour le 694.

### Gaps
- Comportement Wi-Fi d'un 600 **hors de la base** : je n'ai trouvé aucune source sur une éventuelle coupure du Wi-Fi après un délai d'inactivité ni sur sa durée. Seuls des rapports anecdotiques existent (connexion réussie robot à l'arrêt hors base ; robot joignable seulement en nettoyage).

## Q5. Situation 2025–2026 : finances et propriétaire d'iRobot, cloud, application, firmware, contrôle local sans cloud

### Takeaway
iRobot a déposé le 14 décembre 2025 une procédure de **chapter 11 « pré-négociée »**. Son fabricant et prêteur **Picea** (Shenzhen PICEA Robotics et Santrum Hong Kong) en a pris **100 %** le **23 janvier 2026**. iRobot est désormais privée, avec une filiale américaine « iRobot Safe » dédiée aux données. La société a annoncé « no anticipated disruption to its app functionality » ; c'est une déclaration d'intention, pas une garantie dans la durée. Je n'ai trouvé **aucun rapport 2025–2026 de mise à jour qui aurait désactivé le contrôle local d'un 600**. La page officielle des firmwares 600/800 s'arrête en 2020. Le contrôle local ne dépend pas du cloud une fois les identifiants connus (fonctionnement hors ligne rapporté). En revanche, la récupération cloud du mot de passe et la configuration Wi-Fi initiale par l'application en dépendent.

- Le risque principal pour un 694 n'est pas une coupure du contrôle local, mais : (a) la disparition éventuelle du cloud, qui empêcherait de récupérer le mot de passe par cette voie et d'utiliser l'application pour reconfigurer le Wi-Fi après une réinitialisation ; (b) une mise à jour OTA, peu probable vu l'absence de nouvelle version publiée depuis 2020 pour les 600/800, mais impossible à exclure.

### Gaps

## Q6. Le 694 expose-t-il une autre API locale (HTTP/REST, etc.) ?

### Takeaway
**Aucune autre API locale n'est documentée pour le 694.** Les seuls services locaux décrits sont la découverte UDP 5678 et le MQTT/TLS 8883, sur lequel passe aussi la récupération du mot de passe. L'API HTTP n'existait que sur les anciens firmwares 1.6.x (premiers 980). Les API REST citées (rest980, serveur web de Roomba980-Python) tournent sur **votre** machine, pas sur le robot. Matter ne concerne que des modèles récents.

### Cited Findings
- Tableau dorita980 : « HTTP API | yes | yes | - | - | - » (1.6.x Local et Cloud : oui ; 2.x.x et 3.x.x : non) [non confirmé] — [README dorita980](https://github.com/koalazak/dorita980).
- rest980 « create a http server to map all dorita980 methods in a REST API », à lancer sur votre machine (`PORT` par défaut 3000) — [README rest980](https://github.com/koalazak/rest980). Le serveur web de Roomba980-Python (« webport=8200 ») tourne lui aussi sur l'hôte — [README Roomba980-Python](https://github.com/NickWaterton/Roomba980-Python).
- Services observés sur le réseau : UDP 5678 (`irobotmcs`), MQTT/TLS 8883 — [roombapy discovery.py](https://github.com/pschmitt/roombapy/blob/main/roombapy/discovery.py), [roombapy getpassword.py](https://github.com/pschmitt/roombapy/blob/main/roombapy/getpassword.py). Home Assistant écoute aussi l'annonce zeroconf `_amzn-alexa._tcp.local.` des hôtes `roomba-*`, qui sert uniquement à la découverte — [HA manifest.json](https://github.com/home-assistant/core/blob/dev/homeassistant/components/roomba/manifest.json).
- Matter : seulement Plus 500 Combo, Max 700 et Combo 10 Max (voir Q5) — [iPhone in Canada](https://www.iphoneincanada.ca/2025/12/30/apple-homekit-and-matter-support-come-to-more-roomba-vacuums/).

### Inferences
- L'annonce `_amzn-alexa._tcp` suggère un service lié à Alexa sur le robot. Aucune source ne le décrit comme une API utilisable [non confirmé].

### Gaps
- Je n'ai trouvé aucun scan de ports publié pour un 600 Wi-Fi ou un 694. Il est donc impossible d'affirmer qu'aucun autre port n'est ouvert : je peux seulement dire qu'aucun n'est documenté.
